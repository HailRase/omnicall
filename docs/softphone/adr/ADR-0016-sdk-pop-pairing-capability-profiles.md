# ADR-0016: SDK Proof-of-Possession, Pairing Ceremony, and Capability Profiles

## Type

DOCUMENT.

## Status

Accepted (2026-07-20) — closes **O-POP-1**, **O-POP-2**, **O-CAP-1** (SDK-01; shared freeze with DI-04)

## Context

- **Features:** F-011
- **Legacy:** LF-080, LF-081
- **Roadmap:** P12
- **Contexts:** Integration, Settings
- **Layers:** Main pairing store, `@axatalk/sdk` auth, Settings UI (DI-09)

ADR-0011 closed Origin, pairing requirement, capability names, replay, and revoke policy.
Cryptographic proof-of-possession, approve payload shape, and default capability profiles
were left to SDK-01 so DI-03 transport cannot invent them.

## Decision

### O-POP-1 — Proof-of-possession

1. **Algorithm:** Web Crypto **ECDSA P-256** (`ECDSA` + `P-256` + `SHA-256`). Chosen for
   broad Chromium/Firefox secure-context support. Ed25519 may be added later as an additive
   algorithm id without removing P-256.

2. **Key lifecycle:**
   - On first pair, the SDK generates a non-extractable `CryptoKey` pair in the browser.
   - Public key (SPKI, base64url) is sent only inside the pairing request over the already
     Origin-gated WebSocket.
   - Private key remains non-extractable; persisted only via Web Crypto + **IndexedDB**
     (never `localStorage` / `sessionStorage`, never URL/query/fragment).
   - Desktop stores the public key + client metadata via `SecretStoragePort` / approved
     secure service (ADR-0011). Private keys never leave the browser.

3. **Authentication after pairing:**
   - Server hello includes `authChallenge`: `{ challengeId, nonce, expiresAt }`.
   - Client responds with `authProof`: `{ challengeId, clientId, signature }` where
     `signature` is ECDSA-P256-SHA256 over a canonical bytestring:
     `v1|{serverInstanceId}|{sessionEpoch}|{origin}|{clientId}|{challengeId}|{nonce}`.
   - Mismatch, expiry, unknown client, or bad signature → fail closed (`unauthenticated` /
     connection close per fixtures). No snapshot before success.

4. **Replay:** `challengeId` and `nonce` are single-use within a bounded server cache.
   Replayed proofs fail closed.

### O-POP-2 — Pairing ceremony / approve payload

Wire shapes (schemas land in SDK-02; semantics frozen here):

**Client → server `pairing:request`**

```json
{
  "type": "pairing:request",
  "clientId": "<uuid v4 generated by SDK installation>",
  "clientPublicKey": "<base64url SPKI>",
  "keyAlgorithm": "ECDSA-P256-SHA256",
  "application": { "name": "string", "version": "string" },
  "requestedProfile": "presentation" | "operator" | "call_controller",
  "requestedCapabilities": ["session.read.redacted", "..."]
}
```

**Server → client `pairing:pending`**

```json
{
  "type": "pairing:pending",
  "pairingRequestId": "<opaque>",
  "expiresAt": "<iso>"
}
```

**Desktop local approve (Settings / system prompt; not a browser secret):** operator
confirms Origin, app name, requested profile. Desktop persists binding
`{ clientId, origin, publicKey, profile, grantedCapabilities, createdAt }`.

**Server → client `pairing:approved` | `pairing:denied`**

```json
{
  "type": "pairing:approved",
  "clientId": "<uuid>",
  "grantedCapabilities": ["..."],
  "profile": "presentation"
}
```

Denied returns stable `forbidden` / pairing-denied code without capabilities.
No pairing material is placed in discovery, npm bundles, or deep links.

### O-CAP-1 — Default capability profiles

Profiles are **defaults at approve time**. Desktop may grant a subset; server-issued
grants remain authoritative on every command (ADR-0011).

| Profile | Default granted capabilities |
| --- | --- |
| `presentation` | `session.read.redacted`, `window.show` |
| `operator` | presentation + `operator.status.write`, `session.logout` |
| `call_controller` | operator + `call.originate`, `call.control` |

Privileged capabilities **never** appear in default profiles:

- `account.activate` — short-lived grant + local approval (DI-08 / ADR-0013)
- `window.hide` — unavailable in protocol v1 product surface (ADR-0013)

Requested capabilities outside the selected profile are ignored or require explicit admin
override in Settings (DI-09); they are never auto-escalated from the browser.

## Alternatives Considered

| Alternative | Why not |
| --- | --- |
| Shared static bearer in CRM config | XSS forever; forbidden by SECURITY.md |
| HMAC secret in `localStorage` | Extractable; storage policy violation |
| Origin-only trust | Insufficient (ADR-0011) |
| Ed25519-only | Weaker universal availability vs P-256 at decision time |

## Consequences

- SDK-04 / DI-04 implement challenge-response and pairing UX against these shapes.
- Security tests cover replay, wrong origin, revoked key, and capability escalation.
- Rollback: revoke client or disable gateway; calls/sessions continue (ADR-0011).

## Architecture Checks

- Domain never sees private keys or pairing secrets.
- Settings projections never expose reusable bearer secrets.
- Capabilities fail closed on every command.
