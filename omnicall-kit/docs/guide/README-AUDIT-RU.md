# Аудит документации OmniCall Kit

**Дата:** 2026-07-28  
**Объект:** корневой `README.md` и связанный с ним `docs/guide/RU-DEVELOPER-GUIDE.md`  
**Источник API:** `etc/api/sdk.api.md` (API Extractor).

## Краткий вывод

Корневой README хорошо описывает устройство workspace и выпуск пакетов, но не
помогает CRM-разработчику подключить SDK. Он отсылает читателя в другой документ
уже на 24-й строке. Подробный русский гайд содержит почти всю нужную информацию,
но перегружен внутренними терминами и объединяет справочник, правила безопасности
и рецепты в один документ на 766 строк.

Новый README должен стать точкой входа для интегратора. Внутренние детали выпуска
и разработки workspace следует оставить в специализированных документах.

## Читабельность и сложность языка

### Оценка метрик

Метрики приблизительные: Markdown, таблицы, имена типов и фрагменты кода не
соответствуют модели Flesch буквально.

| Документ | Оценка удобочитаемости | Средняя длина предложения | Средняя длина абзаца | Вывод |
| --- | ---: | ---: | ---: | --- |
| Корневой `README.md` | около 50/100 | 15–18 слов | 1–2 предложения | Короткий, но адресован сопровождающему пакета, а не пользователю SDK |
| `RU-DEVELOPER-GUIDE.md` | около 25/100 | 20–25 слов без кода | 2–4 предложения, много таблиц | Фактически полный, но требует уверенного знания протоколов, телефонии и внутренней архитектуры |

Низкая оценка гайда вызвана не русским языком как таковым, а плотностью
сокращений, англоязычных идентификаторов, составных предложений и ссылок на ADR.
Например, формулировка «Pairing + PoP-сессия к loopback WebSocket gateway» вводит
четыре специальных понятия до того, как они определены.

### Термины, которые требуют простого объяснения

| Термин | Простое определение |
| --- | --- |
| SDK | Набор кода, который вы подключаете в своё приложение, чтобы работать с OmniCall. |
| CRM | Веб-приложение, в котором оператор ведёт клиентов и звонки. |
| Gateway | Локальная точка связи в OmniCall Desktop, принимающая запросы SDK. |
| WebSocket | Постоянное соединение браузера с программой, по которому обе стороны могут отправлять сообщения. |
| loopback | Адрес компьютера пользователя (`127.0.0.1`), доступный только на его устройстве. |
| pairing | Первое явное подтверждение, что конкретный сайт может подключаться к OmniCall Desktop. |
| Origin | Схема, домен и порт сайта, например `https://crm.example`; Desktop сравнивает эту строку целиком. |
| PoP | Криптографическое доказательство, что повторное подключение делает тот же браузер, который прошёл pairing. |
| capability | Разрешение на отдельное действие, например совершить звонок или изменить статус оператора. |
| snapshot | Полный согласованный снимок текущего состояния Desktop для построения интерфейса. |
| revision | Номер версии снимка. Он защищает от действия по устаревшему состоянию. |
| mutation | Команда, которая меняет состояние: звонок, смена статуса или выход. |
| FSM | Набор допустимых состояний и переходов между ними. Интегратору не нужно реализовывать его в CRM. |
| SIP | Сетевой протокол телефонии. SDK не работает с ним напрямую. |
| OCP | Внутренний протокол операторской платформы. SDK не передаёт его данные в CRM. |
| Trusted sites | Список exact Origin, которым разрешён WebSocket к Desktop. До `connect()` CRM Origin должен быть `allowed` (Settings или seed). Исторический TOFU-on-upgrade отключён (ADR-0018, 2026-08-03). |
| redacted | Данные, из которых удалены или замаскированы чувствительные части, например номер телефона. |
| jitter | Небольшая случайная поправка задержки повторной попытки, чтобы клиенты не подключались одновременно. |
| idempotent | Операция, которую безопасно повторить без изменения результата. Звонки и logout к таким операциям не относятся. |
| LNA | Разрешение браузера на связь HTTPS-сайта с программой в локальной сети или на компьютере пользователя. |
| DTO | Объект данных, который передаётся между частями системы. |
| wire | Формат сообщений внутри сетевого соединения. Он не является API для CRM. |
| anti-corruption layer | Граница, которая не даёт внутренним понятиям одной системы проникать в другую. |

Текущий порядок корневого README логичен для команды выпуска: workspace → release →
локальные команды. Для пользователя библиотеки он обратный: прежде чем увидеть
установку и пример, читатель встречает организацию npm и правила релиза.

## Полнота покрытия API

`etc/api/sdk.api.md` содержит 77 экспортов: фабрики, интерфейсы, типы,
константы, класс ошибки и re-export типов протокола. Корневой README не
документирует ни одну сигнатуру публичного SDK.

Русский гайд покрывает основные namespaces `client.calls`, `client.window`,
`client.account`, `client.operator`, состояния, события и классы ошибок. Однако
для следующих публичных частей отсутствует полное описание сигнатуры, параметров,
результатов и работающего примера:

- `createAuthClient`, `AuthClient` и его lifecycle-методы;
- `createBrowserWebSocketTransport`, `TransportPort` и связанные типы;
- `createBrowserScheduler`, `createBrowserJitterSource`, `Scheduler`,
  `JitterSource`, `TimerHandle`;
- тестовые инструменты `createFakeScheduler`, `createFixedJitterSource`,
  `FakeScheduler`;
- диагностический инструмент `createRecordingDiagnosticsSink` и типы
  `DiagnosticEvent`, `DiagnosticsSink`;
- все операции `PopKeyStore`, тип `StoredPopIdentity`;
- точная структура `ReconnectPolicy` и `HeartbeatPolicy`;
- структуры результатов: `CallMutationResult`, `LogoutResult`,
  `ActivateProfileResult`, `OperatorStatusChangeResult`;
- типизированные события `OmniCallEvent` и `OmniCallEventOf`;
- константы времени activation;
- структура `SnapshotMessage`, `SnapshotSections`, `SnapshotCallSummary` и
  перечисления, re-exported из пакета protocol.

Кроме того, в API report помечены как undocumented `CallMutationResult`,
`ConnectionState`, диагностические типы и транспортные типы. Это не означает, что
их нельзя использовать: они экспортируются публично. Это означает, что
документация должна либо описать их, либо явно обозначить как низкоуровневые API
для интеграционных тестов.

## Качество примеров

Сильные стороны:

- примеры правильно используют `expectedRevision`;
- показаны `stale_state`, `interaction_required` и `sip_not_registered`;
- предупреждения не повторять мутации после reconnect технически корректны.

Недостатки:

- минимальный пример требует одновременно понять IndexedDB, PoP, Origin, profile,
  capabilities и lifecycle;
- в ряде листингов переменные намеренно нейтрализуются через `void`, поэтому
  читатель не получает видимого результата;
- примеры разбросаны по скрытым блокам `<details>` и не образуют один
  копируемый сценарий;
- код не показывает, как отобразить pairing-required, состояние ready и
  фактическую ошибку пользователю;
- для транспорта, scheduler, diagnostics и `AuthClient` нет самостоятельных
  примеров;
- ссылки на runnable fake peer полезны, но README не объясняет, как его запустить.

## Работа с понятиями

Ключевые понятия в гайде есть, но вводятся после их первого использования или
смешиваются с деталями реализации. В частности, сначала используются pairing,
PoP, snapshot, revision и capability, а их смысл раскрывается позднее и частично
на английском. Понятия `SIP`, `OCP`, `Domain Event`, `FSM`, `ADR` и
`anti-corruption` не нужны для первого подключения и должны быть вынесены в
границы SDK либо объяснены при первом употреблении.

## Рекомендации, реализуемые в новом README

1. Начинать с результата: CRM получает снимок состояния и отправляет безопасные
   команды в уже установленный Desktop.
2. Объяснить пять базовых понятий до первого кода: Desktop, pairing, capability,
   snapshot и revision.
3. Дать одну пошаговую копируемую последовательность от `npm install` до
   `getSnapshot()`.
4. Описать каждый метод клиента отдельно; низкоуровневые и тестовые экспорты
   отделить от стандартной интеграции.
5. Превратить ошибки и ограничения в FAQ «симптом → причина → действие».
6. Указать, что лицензия в репозитории не объявлена, вместо ложного заявления.
